## v1.2.0 同步容量优化（同日追加）

用户反馈「一键收藏 64 个标签页报同步失败」，根因是 100KB 配额超限。用户选定方案 A（瘦身+压缩）：

- **v2 存储格式**：favicon 字段不参与同步（读取端域名推导）+ 全量 gzip（CompressionStream）+ base64 按 6KB 分片存 `mn:data:N`，`meta.format=2` 标识
- **兼容 v1**：明文分片 `mn:bm:N/mn:gr:N` 可读，首次 v2 写入后自动清理旧分片
- **实测收益**：1200 条书签 v1 需 455KB → v2 仅 66KB，容量约 5~7 倍（1000~2000 条）
- 容量预检改为异步真实压缩估算；`addBookmark/addBookmarks` 变 async（返回 Bookmark|null / Promise<number>，-1 表示超限）
- git hook 要求 commit 正文至少 2 条「- 描述」格式

## v1.3.0 增量同步 + 标签去重（同日追加）

- **存储格式 v3**：书签按 order 排序切组（GROUP_RAW_LIMIT=20_000 原始字节 ≈ 50 条/组，压缩后 base64 约 4KB），每组独立 gzip 存 `mn:bg:N`；分组（文件夹）整体压缩存 `mn:grp:N`。saveState 先 get 云端现有组、逐 key 比对，只 set 变化的组 → 增量写入。
- **实测**：1000 条 v3=65KB（v2 整体 56KB，多 16% 开销换增量）；新增书签只写末组 ~1.8KB（全量 65KB，36 倍减少）。分组过小（2800B≈7条）会严重损失压缩率（94KB），20KB 是实测最优点。
- 兼容读取 format 3/2/1；写 v3 后清理 v2 `mn:data:*`、v1 `mn:bm:*`/`mn:gr:*` 与多余组。
- **重复标签**：utils `findDuplicateTags`（NFKC+小写+去空白归一），TagDialog 显示重复组并一键合并（renameTag 到规范写法，带撤销）。
